# Agent Kit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local stdio MCP server, the agent kit, that lets any MCP client work, post and pay Deplace bounties on https://deplace.space with its owner's agentWallet key, under rails that hold whatever the model asks.

**Architecture:** The kit lives in `agent/` next to the reference agent and reuses its signer, guard, budget and x402 client. Shared step functions (`agent/src/steps.ts`) hold each board sequence once: the reference agent sends through `directSend`, the kit through `Relay`, which adds a signing queue, an account lock, pending records written before sending, and lost-answer resolution. `BoardLink` wraps the board's MCP endpoint with retries before signing, reconnects and the session. `buildKitServer` exposes twelve tools on stdio.

**Tech Stack:** TypeScript (ESM, Node 24.19 here, engines ≥ 22.5), tsx 4.23.15, @modelcontextprotocol/sdk 1.32.2, zod 4.6.7, @concordium/web-sdk 12.0.3, @x402/core, @x402/concordium and @x402/fetch 2.32.0, vitest 5.1.1.

**Spec:** `docs/superpowers/specs/2026-11-23-agent-kit-design.md` (approved 23 Nov 2026, commit 55c0f48). Read it before starting; this plan argues from it.

## Global Constraints

- Work on `main`, no branches. Each task ends with one commit whose message is a single Conventional Commits line; the repo's git config already commits as `KAMEVETRICS <96529122+KAMEVETRICS@users.noreply.github.com>`. Task 13 pushes.
- Never commit `secrets/`, `.env` or `data/`. Never print, log or type a key.
- Never start a local board (`npm start -w server`) against contract 13123. Live runs use https://deplace.space only.
- `server/public/agents/bounty-worker.json` must not change by one byte. No changes under `server/`, `web/` or `contracts/`.
- Nothing under `agent/src/kit/`, and nothing it calls, writes to stdout: stdout carries MCP messages only. Logging goes through an injected `log` that writes to stderr.
- The kit reads settings only from `process.env` (the MCP client's `env` block, or `node --env-file`). It never imports `agent/src/env.ts` and never reads the repo's `.env`.
- Kit defaults: `BOARD_MCP_URL=https://deplace.space/mcp`, `CONTRACT_INDEX=13123`, `CONTRACT_SUBINDEX=0`, `REGISTRY_INDEX=12802`, `REGISTRY_SUBINDEX=0`, `AGENT_ALLOW_FEES=false` with a 30,000 energy cap, `AGENT_MAX_REWARD=5`, `AGENT_DAILY_BUDGET=20`, `AGENT_BUDGET_FILE=data/agent-budget.json`, `AGENT_PENDING_FILE=data/agent-pending.json`, `GRPC_HOST=grpc.testnet.concordium.com`, `GRPC_PORT=20000`, `REWARD_TOKEN_ID=EUDemo`, `AGENT_CARD_FILE=data/agent-card.json`. Relative paths resolve against the repo root.
- Limits checked before anything is prepared (the board's own): bounty id `^\d{1,20}$`; `preview` ≤ 2,000 characters; `full` 1 to 100,000; title 1 to 120; description ≤ 4,000; `task_kind` `^[a-z0-9-]{1,32}$`; `input` a JSON object under 2 KB; `deadline_hours` > 0 and ≤ 2,160; `reason` 1 to 2,000.
- Retries happen only before signing, within one 30-second deadline per tool call. `submit_signed` is never retried.
- A transaction's hash is `sha256(Transaction.serializeBlockItem(Transaction.finalize(signed)))`, for both transaction versions: those are the bytes `sendTransaction` sends for a version 1 transaction, and the rule `server/src/chain/operator.ts` uses for version 0. Never `Transaction.getAccountTransactionHash`: it gave a different value for a sponsored transaction when checked on 23 Nov.
- Tool results and logs never contain keys, signatures or transaction JSON.
- Subagents run on Sonnet.

## Review Focus

1. A bounty title with spaces around it: the board hashes `title.trim()`, so the kit must too, or every such post is refused. Test in Task 1.
2. A reward of "0.0000001", "1,5", "-1" or "1e3": refused with a clear message before anything is prepared or booked. Test in Task 8.
3. A bounty id with leading zeros ("005"): sent to the board as "5" and expected as 5n, so the claim gets signed. Test in Task 7.
4. Windows key paths (backslashes, spaces, relative to the repo): `AGENT_KEY_FILE` resolves to the right file. Test in Task 9.
5. The board unreachable when the kit starts or mid-session: the kit still starts and lists its tools, a call returns `retryable: true` within its deadline, and the next call after the network returns works. Tests in Tasks 5 and 9.

All commands below run from the repo root unless a step says otherwise. Agent tests: `npm test -w agent -- <file>`.

- [ ] **Step 3: Implement.** `PendingStore` keeps a JSON array, writes it with `writeFileSync` (creating the folder), reads a missing file as empty, and throws on a corrupt one. `AccountLock` writes `{ pid, since }` with `openSync(file, "wx")`. **Files:**

**Interfaces:**
- Consumes: `checkPrepared`, `signPrepared`, `transactionHash`, `PendingStore`, `AccountLock`, `LockHeld`, `SpendBudget`, `KitChain`, `Send` and `SendStep` (`steps.ts`), `BoardConfigView`, `KitError`.
- Produces:
  ```ts
  export interface RelayBoard { relay(txJson: string): Promise<Relayed>; config(deadline?: number): Promise<BoardConfigView> }
  export interface RelayOptions {
    board: RelayBoard; keys: AgentKeys; guard: GuardOptions;
    chain: Pick<KitChain, "txOutcome" | "finalizedNonce">;
    pending: PendingStore; lock: AccountLock; budget: () => Promise<SpendBudget>;
    now?: () => number; log: (m: string) => void;
  }
  export type Settled =
    | { record: PendingTx; landed: true; failed: boolean; events: BoardEvent[]; link: string }
    | { record: PendingTx; landed: false };
  export class Relay {
    constructor(o: RelayOptions);
    /** One signing turn at a time. Takes the account lock (LockHeld becomes a KitError naming the pid), refuses with RailViolation when the board's /config names another contract than guard.contract, and runs settlePayments() first. */
    turn<T>(fn: () => Promise<T>): Promise<T>;
    /** For steps.ts, inside a turn: checkPrepared with step.expected, sign, step.onSigned(hash), pending.add({ kind: "tx", …, expiresAt from the header, commitRef: what onSigned returned }), board.relay. A normal answer removes the record; any failure keeps it. When the board's txHash differs from transactionHash(), refuses all further signing in this process. */
    readonly send: Send;
    /** Inside a turn: settles pending transactions matching `match` by their hash, returns and removes the settled ones, and throws KitError(true, { retryAfter }) while one may still land. */
    settle(match: (r: PendingTx) => boolean): Promise<Settled[]>;
    /** Inside a turn: the nonce rule for pending payments; KitError(true, { retryAfter }) before a payment's expiry. */
    settlePayments(): Promise<{ landed: string[]; released: string[] }>;
  }
  ```
- `settle`, per record:
  - `finalized`: settled as landed. With a `commitRef`, a `Posted` event leads to `rename(commitRef, "bounty:<id>")`, and a failed transaction to `remove(commitRef)`.
  - `pending`: throw unresolved.
  - `absent` after `expiresAt`: settled as not landed, with `remove(commitRef)` when there is one. Before `expiresAt`: throw unresolved.
- `settlePayments`, per record:
  - Before `expiresAt`: throw unresolved.
  - `finalizedNonce(account) <= BigInt(nonce)`: `unbook(ref, amount)`, remove the record, and list it as released.
  - Above the nonce: remove the record, keep the booking, and list it as landed.

**Interfaces:**
- Consumes: `KitDeps`, `bountyIdOf` (Task 7), `postStep`, `posterActionStep`, `rejectStep`, `awardStep`, `payStep` (Task 4), `Relay` (Task 6).
- Produces:
  ```ts
  export interface HireTools {
    post_bounty(a: { title: string; description: string; task_kind: string; input: Record<string, unknown>; kind: BountyKind; reward: string; deadline_hours: number; escrow?: boolean }): R;
    fund_bounty(a: { bounty_id: string }): R;
    accept(a: { bounty_id: string }): R;
    reject(a: { bounty_id: string; reason: string }): R;
    award(a: { bounty_id: string; entry_id: number }): R;
    cancel(a: { bounty_id: string }): R;
    get_work(a: { bounty_id: string }): R;
  }
  export function hireTools(d: KitDeps): HireTools;
  ```
- Behaviour:
  - `post_bounty`, in a turn:
    1. Settle every pending `post` first. If one landed, report it ("your earlier post went through as bounty N; nothing new was posted") and stop.
    2. `deadline = now + deadline_hours × 3,600,000`.
    3. Get decimals from `chain.decimals(token.id)`. A reward that `parseTokenAmount` refuses, or that comes to 0, becomes a KitError (not retryable) before `prepare_post`.
    4. `postStep`, then with `escrow`, the `fund_bounty` sequence in the same turn.
  - `fund_bounty`: on chain the bounty must name this account as poster and be NotFunded. `prepare_fund` gives the URL; `payStep` runs with `POST` and `expected` set to the escrow account on chain (`chain.escrowAccount()`) and the reward on chain. `purpose` is `"fund"`.
  - `fund_bounty` and `get_work`: a transport error from `payStep` becomes KitError(true, { outcomeUnknown: true, retryAfter: <the payment's expiry> }), and the message says the kit will check the payment after then.
  - `accept`, `reject`, `award` and `cancel`: in a turn, after settling pending records of the same action and bounty.
  - `get_work`: in a turn, `fetch_work`. When no payment is required, it returns the items. Otherwise the payee comes from `chain.payee(chain.bounty(id))`, then `payStep` runs with `GET`, the reward on chain and `purpose: "deliver"`, and it returns the items and the payment link. When `settlePayments` has listed this bounty as landed and the board still asks for payment, it refuses with "the payment for bounty N went through on chain, but the board hasn't recorded it yet; ask the board's operator".
- Schemas: `title: z.string().min(1).max(120)`, `description: z.string().max(4000)`, `task_kind: z.string().regex(/^[a-z0-9-]{1,32}$/)`, `input: z.record(z.string(), z.unknown())` (the tool refuses one whose JSON is over 2,048 characters), `kind: z.enum(["Exclusive", "Contest"])`, `reward: z.string()`, `deadline_hours: z.number().positive().max(2160)`, `escrow: z.boolean().optional()`, `reason: z.string().min(1).max(2000)`, `entry_id: z.number().int().min(0)`.
- Tool descriptions (exact copy):
  - `post_bounty`: "Post a bounty paid in EUDemo. reward is a decimal amount; your owner caps each reward and the total per 24 hours. escrow: true moves the reward into escrow now; otherwise you pay the worker on delivery with get_work."
  - `fund_bounty`: "Escrow the reward of a bounty you posted. The kit pays only the escrow account the contract names."
  - `accept`: "Accept the submitted work on your bounty. Escrowed rewards are then paid out by the escrow."
  - `reject`: "Send submitted work back with a reason. The third rejection is final and goes on your public record."
